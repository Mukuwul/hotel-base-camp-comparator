01

Problem understanding

Which hotel do you actually book?

Imagine you and a group of friends are finally taking the city trip that has lived in the group chat for months. Everyone has already agreed on the wishlist — a famous landmark, a museum, a night market, a riverside walk, a few food spots nobody wants to miss.

There is one argument left. A cheap hotel might leave you crossing the whole city every single day. A hotel right next to the most popular spot might eat the entire budget. And phrases like "centrally located" settle nothing, because they compare nothing.

What this tool does

You give it one budget for the complete stay, and you say how much each place on the wishlist actually matters to your group, from 1 to 5. It then compares every hotel's whole-stay price against the known round-trip travel time to every single place — and recommends the most accessible hotel you can actually afford.

A worked example, straight from the problem statement. Suppose CLOCK matters 3 and MARKET matters 2. A hotel with round trips of 20 and 40 minutes scores (3 × 20) + (2 × 40) = 140 importance-minutes, a weighted average of 140 / 5 = 28.0 minutes. Lower is better. A hotel is only in the running when its complete-stay cost is at or below the budget.

The weighting is the whole point: a medium trip to somewhere the group is excited about outweighs a short hop to somewhere nobody cares about. And because every number is shown on screen, nobody has to take the answer on trust — the working is visible, place by place.

What it deliberately is not

Not an itinerary planner. It does not choose places, arrange days, find routes, or estimate meals, tickets or transport. It answers exactly one question — where should we base ourselves — and it answers it with arithmetic rather than adjectives.

The correcting prompt

I want the actual computation/math and validation logic to be completely separate from the React UI. The engine/ files should contain pure, reusable, unit-testable functions such as: validation, contribution calculation, weighted travel total, affordability, ranking, tie-breaking, rounding, final comparison calculation. The UI should only manage state, collect inputs, call the engine functions, and display their results. For example, the core calculation should be directly testable with something like: computeComparison(scenario, 1500, {}) from Vitest, without rendering React components or using React Testing Library. Review the architecture and tell me whether ranking.js is enough or whether we should introduce another engine file such as comparison.js. Keep the architecture simple and avoid unnecessary files.

What actually changed, and why it is the right fix

  • The hook was removed entirely. A hook only runs inside a rendering component — which directly contradicts the requirement in the prompt itself: testable without rendering React. You cannot call a hook the way you call computeComparison(scenario, 1500, {}).
  • computeComparison.js was added as a plain function taking over the hook's composition role. Same logic, zero React dependency — which answers the prompt's own question: one engine file was not enough, and this is the second one.
  • App.jsx changed jobs from wiring a hook to owning state directly and calling the engine each render. State stayed a React concern; arithmetic moved fully out of React.
  • The test file changed with it. useComparator.test.js would have needed hook-testing tooling. computeComparison.test.js needs nothing but plain function calls.

The project's own written record confirms this was a reasoned trade-off rather than an accident: "A custom useComparator hook wrapping the state — considered and dropped. The only justification for extracting a hook is reuse across multiple components, and there's exactly one consumer (App.jsx) here… the isolated-testability it offered comes just as well from computeComparison() being a plain function."

ARCHITECTURE.md — Alternatives considered and rejected

The one rule everything else follows: engine/ never imports React. App.jsx never contains calculation logic — only useState and JSX.

Process · how the build was actually run

Five files that governed the work

The project was not improvised into existence. Before and during the build, five plain Markdown files sat in the project root and constrained what happened next.

RULES.md

The rules the assistant had to follow before answering anything, for the rest of the build:

  1. Never change GOALS.md or POINTS_TO_REMEMBER.md unless explicitly told to — reading, quoting and suggesting are fine; editing on its own initiative is not.
  2. Flag a testing opportunity out loud rather than silently adding a test or silently skipping one.
  3. File-by-file build process: show a file's full content, explain it in very easy English, and wait for questions. Write it only once told to, and commit only when told "commit this file as final."

POINTS_TO_REMEMBER.md

The running build log — what was being considered, decided or ruled out at each point. Entries were added only when explicitly asked for, which makes it a genuine first-person record of the thinking rather than a machine-generated summary written after the fact. Plate 08 shows it mid-build.

IMPLEMENTATION_PLAN.md

The five-stage plan on plate 04, written before any project code, so the order of work — data, validation, ranking, state, UI, tests — was a decision rather than an accident.

GOALS.md

The full requirement checklist copied from STUDENT_GUIDE.md, tracked line by line throughout with [ ] not started, [~] in progress and [x] completed — and a goal was only ever marked complete once there was real evidence for it, not merely because the relevant code existed.

ARCHITECTURE.md

The reference every new file had to match. Combined with the file-by-file rule above, this meant nothing entered the project that contradicted the agreed folder structure, the engine-never-imports-React rule, or the recorded tech-stack reasoning.

Why not Obsidian?

  • Zero context switching. Plain files in the project folder could be read, quoted and updated in the same conversation that wrote the code — no second application, no vault to keep in sync, no copying between two tools during a time-boxed build.
  • The complexity was not needed. Obsidian's real strengths — bidirectional links, graph view, plugins — serve a large sprawling knowledge base. This project needed five small flat files. Adding a second tool for that is exactly the "unnecessary complexity merely for the sake of using more technologies" the Student Guide warns against.
  • Documentation travelled with the code. Same folder, same repository, same visibility to anyone opening the project — as Figure 6.1 shows. A vault living elsewhere is one more place to remember to check.

The tool was matched to the actual size of the problem — the same principle that chose the tech stack on plate 05.

07

Deliverable 3 · problem solving

Building the dataset: stop guessing, start searching

The specification demands a 10-hotel, 15-place city whose roughly 175 numbers satisfy six story conditions simultaneously. The first approach was to ask for that dataset directly. It did not work, and the reason is worth stating precisely.

Why asking for the numbers failed

Condition 2 alone — the single most accessible hotel overall must be unique, and must be the one just outside the budget — requires comparing every hotel's weighted total against every other hotel's. That is not a judgement that can be made by inspection while also holding five other conditions true. The datasets that came back looked plausible and quietly broke one condition or another almost every time.

The fix: generate candidates, verify in code

The next prompt asked for a script instead of a dataset — one that generates random candidate numbers and checks all six conditions in code, discarding anything that fails and retrying until a candidate passes all six at once. This changes the assistant's job from "guess correct numbers", which is unreliable, to "write correct checking logic", which is verifiable. The numbers themselves then come from brute-force search.

The debugging story worth telling. The first run used wide ranges — stay costs 2,000–9,000, travel times 5–180 — and found nothing in 200,000 attempts. The reason is recorded in the script itself: condition 6 needs one place's importance change to flip the winner, and a single place can only shift a hotel's total by at most four times its travel time. With times reaching 180, the totals were spread too far apart for any single place to bridge the gap between the top two hotels. Narrowing to costs 3,000–7,000 and times 10–140 made near-ties common — and a valid dataset appeared in 5,754 attempts, in 0.1 seconds.

Boundary worth stating out loud: this is a build-time tool. The application never runs it and never randomises anything — the winning output was pasted into src/data/demoCity.js as fixed constants, so the identical city materialises on every load and every reset. And the script checking its own output is not the independent verification the specification requires; that is done separately, in tests/demoCity.test.js, which re-derives every value with its own arithmetic.

Deliverable 2 · working solution

The application, and the working shown

To run it: cd project, then npm install, then npm run dev. No backend, no database, no API keys, no network access — the city is compiled in as constants, so the identical scenario loads every time and Reset returns to it exactly.

The demonstration script

  • Load. 25 labelled markers, 7 ranked hotels, 3 marked over budget, Lantern Court Inn recommended.
  • Inspect. Click any hotel — exactly 15 links appear, from that hotel only, and the breakdown table below updates. Hover a link for place — X min × importance Y = Z.
  • Cross the budget boundary. Set the budget to 6,790 and The Meridian takes rank 1. Set it to 6,789 and it returns to over budget by 1.
  • Flip on importance. Change Glasswing Gardens from 4 to 1 — the recommendation moves to Copperline Lodge, and the box shows was 4.
  • Break it deliberately. Type 9 into any importance box — the error banner appears and the entire ranking disappears rather than showing a stale one.
  • Empty the budget. Set it to 0 — NO_AFFORDABLE_HOTEL, with no leftover winner.
  • Reset. Everything returns to the starting state exactly.

Student_SPR26_D2_P03 — Acceptance Criteria

Rather than adding a feature to the application, this is presented as an analysis derived from the shipped dataset and the shipped ranking rules — a documented answer to the same question the optional feature would have asked.

How it is derived

Walk the hotels in ascending order of stay cost. Each becomes affordable exactly at its own price; at that moment, check whether its weighted travel total beats the best affordable total so far. If it does, the recommendation changes there. If it does not, nothing changes until the next hotel's price is reached.

Budget rangeRecommendedTotalWhy it changes here
0 – 3,059——Nothing is affordable yet, so the result is NO_AFFORDABLE_HOTEL.
3,060 – 3,189DOCKSIDE3,687The cheapest hotel becomes affordable at its own price and is the only candidate.
3,190 – 6,789LANTERN_COURT2,821Becomes affordable and immediately beats Dockside's score. Holds the recommendation across the widest range — including the initial budget of 4,730.
6,790 and aboveMERIDIAN2,815The best-scoring hotel overall finally becomes affordable at its own price — story condition 5, exactly.

Seven hotels become affordable somewhere between 3,190 and 6,789 — Saltwind, Foxglove, Maple & Vine, Copperline, Harbour Gate, Gilded Anchor and Ridgeview — and not one of them beats Lantern Court's 2,821, so the recommendation does not move at all across that entire stretch.
